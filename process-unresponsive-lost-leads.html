Unresponsive Lost Leads Automation

Auto-closing dead follow-up leads in ActiveCampaign — while protecting the ones sales is still working

MAG runs two email follow-up sequences whose state lives in Supabase. When a lead reaches the last email of its sequence and never replies, its ActiveCampaign (AC) deal should be marked Lost, the contact tagged, and a note left on the deal — so the sales pipeline reflects reality without anyone doing it by hand. This automation does that cleanup every week. Just as importantly, it now leaves alone any lead the sales team is still actively working, so a genuinely live opportunity is never closed by mistake.

What it does

Every week the automation finds each lead that received the final email of its follow-up sequence, never replied, and has not already been closed out. For each of those leads it performs three ActiveCampaign actions, in order:

  1. Adds a note to the deal explaining the lead did not respond and that the deal is being changed to lost and the contact tagged.
  2. Tags the contact with unresponsive_contact.
  3. Sets the deal status to Lost.

Two email sequences feed the process: the social-media leads (a 4-email sequence) and the cold leads (a 5-email sequence). A lead qualifies once it has received the last email of its own sequence — the 4th for social-media leads, the 5th for cold leads.

The "still being worked" safeguard

Some leads that never reply to the email sequence are still very much alive — a salesperson may have spoken to them and logged a note on the deal after the last email went out. Those leads must never be auto-closed.

So before making any change, the automation checks the deal's notes in ActiveCampaign:

  • It looks at the most recent deal note written by someone other than the automation account. Notes left by the automation account (Julienne's login, which drives most automations) don't count as a sign of human activity.
  • If that most recent human note is dated after the lead's final follow-up email, the lead is treated as still being worked. The automation marks it as skipped and makes no changes in ActiveCampaign — no note, no tag, no status change.
  • Once a lead is marked skipped, it is permanently excluded from future runs.

In practice this catches real cases: for example, a lead whose last email went out on 8 July but whose deal owner added notes on 13 July and 22 July is recognised as active and left open.

When it runs

The automation runs automatically once a week:

  • Every Monday at 6:30 AM Philippine Time (22:30 UTC on Sunday).
  • It is triggered by a scheduled database job that calls the automation over the web; the job simply wakes the process up — all the work happens inside the automation itself.

Because a single run can involve many leads and hundreds of ActiveCampaign calls, the automation acknowledges the trigger immediately and continues the work in the background, so it never runs out of time mid-run. It can also be run on demand for testing, including a mode that processes just a handful of leads at a time.

Safe by design

The automation is built so it can be re-run safely and never double-acts on a lead:

  • Each step is stamped only after it succeeds. The note, the tag, and the "lost" status each record their own completion time on the source record the moment the ActiveCampaign call returns successfully.
  • Partial failures resume cleanly. If a run gets partway through a lead and then fails, the next run picks up exactly where it left off — no duplicate note and no duplicate tag.
  • A lead that can't be checked is left alone. If the automation can't read a deal's notes (for example, a temporary ActiveCampaign hiccup), it does nothing to that lead and retries it next time, rather than risk wrongly closing it.
  • Once closed or skipped, a lead drops out of the working set and is never processed again.

The automation only ever touches its own set of tracking fields; other columns that belong to different processes are left untouched.

How it's built

The pipeline, end to end

  • Scheduled job (pg_cron): a weekly database timer that, every Monday 6:30 AM PHT, sends a web request to wake the automation.
  • Edge function (the automation): a small server-side program that runs the whole process — it asks the database for the qualifying leads, then for each one talks to ActiveCampaign.
  • Database query (a saved SQL function): a single authoritative query that combines both email sequences, joins each lead to its ActiveCampaign contact and deal, filters to leads that finished their sequence and aren't closed or skipped, and returns everything the automation needs — including each lead's final-email date.
  • ActiveCampaign, per lead: read the deal's notes (to run the safeguard check), then — only if the lead is genuinely unresponsive — add the note, add the tag, and set the deal to Lost.
  • Write-back to the database: after each successful ActiveCampaign action, the automation records a timestamp (or the skip flag) on the lead's source record, which is what makes the whole process resumable and one-time-only.

Tech stack

  • Supabase — the database that stores the follow-up sequence records and the tracking fields.
  • Supabase Edge Function (TypeScript / Deno) — where the automation logic runs.
  • PostgreSQL + pg_cron — the database and its built-in scheduler that fires the weekly run.
  • pg_net — the database extension that lets the scheduled job send the web request that starts a run.
  • ActiveCampaign API — the CRM where deals are noted, contacts are tagged, and deals are marked Lost.
